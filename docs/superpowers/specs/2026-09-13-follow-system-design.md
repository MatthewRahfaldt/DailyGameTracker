# Follow System — Design

**Date:** 2026-09-13
**Branch:** `feature/follow-system`
**Status:** Approved for planning

## Problem

There is no way to see what anyone else is playing. A user signs in, pastes a
result, and sees only their own (currently generated) history. This adds a
one-way follow graph and a combined activity feed of the people you follow.

## Scope

**In scope:** the follow graph, follow-by-link, a combined activity feed, and
per-person profile pages.

**Out of scope:** persisting real results. `PasteBox` parses text client-side
and never writes a `GameResult`; no write path exists anywhere in the app. The
feed therefore renders generated data, exactly as `/stats` does today.

This is a deliberate split. The follow graph, the follow codes, and every
permission check are **real** and run against Postgres. Only the result rows
are generated. When result-saving lands, the change is confined to one function
body — the social layer needs no rework.

**Also out of scope:** follow-code regeneration, blocking/muting, follow
approval, notifications, and feed pagination.

## Decisions

| Decision | Choice | Why |
|---|---|---|
| Relationship | One-way follow, no approval | Simplest model that answers "what did my friends play". Following implies results are visible to signed-in followers. |
| Discovery | Share link (`/follow/<code>`) | Email is a poor public identifier: GitHub private-email users get an unguessable `users.noreply.github.com` address, and email search forces people to know each other's private addresses. A link also avoids user enumeration entirely. |
| Main view | Combined reverse-chronological feed | Directly answers "what did my friends do today"; profiles reachable by clicking a name. |
| Real-data stubs | Exported, unused, type-checked | Compiles against the live schema, so it breaks loudly if the model changes rather than rotting as a comment. |
| Pure logic location | `packages/stats` | The only place with a working test runner (`tsx --test`). `apps/web` has no test harness. |

### Rejected alternatives

- **Exact email match** — technically sound (`User.email` is `NOT NULL UNIQUE`,
  and all three providers supply one) but wrong for the job, per the discovery
  reasoning above.
- **Name search** — `name` is populated and human-readable, but it is not
  unique and lets any signed-in user enumerate every account.
- **Mutual friendship / approval flows** — more privacy surface than a
  three-person project needs; revisit if the instance opens up.

## Data model

```prisma
model User {
  // ...existing fields
  followCode String @unique @default(cuid())
  following  Follow[] @relation("follower")
  followers  Follow[] @relation("following")
}

model Follow {
  followerId  String
  followingId String
  createdAt   DateTime @default(now())

  follower  User @relation("follower",  fields: [followerId],  references: [id], onDelete: Cascade)
  following User @relation("following", fields: [followingId], references: [id], onDelete: Cascade)

  @@id([followerId, followingId])
  @@index([followingId])
}
```

- The composite primary key makes double-following impossible in the database
  rather than by application check.
- `@@index([followingId])` serves the follower-direction lookups (profile
  follower counts); the primary key already covers the feed's
  `followerId` lookup.
- Self-follows are blocked by a `CHECK ("followerId" <> "followingId")`
  constraint added in the migration SQL. Prisma cannot express it, and a
  code-only guard leaves the invariant unenforced.

### Migration hazard

`@default(cuid())` is generated by **Prisma Client, not Postgres**. A plain
`ADD COLUMN "followCode" TEXT NOT NULL UNIQUE` fails against existing user rows
(there are currently two). `Group.inviteCode` uses the same pattern but was born
in a `CREATE TABLE` on an empty table.

The generated migration must be hand-edited into three steps:

1. `ADD COLUMN "followCode" TEXT` (nullable)
2. `UPDATE "User" SET "followCode" = gen_random_uuid()::text WHERE "followCode" IS NULL`
3. `ALTER COLUMN "followCode" SET NOT NULL` + `CREATE UNIQUE INDEX`

Run against the shared Supabase project, so use `prisma migrate dev` carefully
and never accept a reset prompt.

## Routes

| Route | Purpose | Access |
|---|---|---|
| `/feed` | Combined activity feed | Signed in |
| `/follow/[code]` | Confirm-and-follow page | Signed in (else sign-in, then return here) |
| `/u/[id]` | One person's profile | Signed in **and** following them, or it's you |

**`GET` never mutates.** Opening a follow link shows a confirmation page —
"Follow **name**?" with a button — and the button posts to a server action. An
automatic follow on `GET` would let a link preview, prefetch, or crawler follow
on the visitor's behalf.

Profiles key on **user id**, not `followCode`: the code is a capability that
grants following, so it must not double as a URL people pass around for reading.
An unauthorized profile returns **404, not 403**, so the page does not confirm
whether an id exists.

## Data flow

`getFeedView(viewerId)` in `lib/demo-feed.ts` mirrors the existing
`getStatsView` shape:

1. Query `Follow` where `followerId = viewerId`, joined to followed `User`
   rows — **real database read**.
2. For each followed user, `makeFixture({ end: today, userId: user.id, seed: seedFrom(user.id) })`
   — the generated part. `seedFrom` hashes the cuid to an int so each person
   gets a different but stable history.
3. Flatten, sort by `playedDate` descending, cap at the trailing 30 days.
4. `isDemo: true`, which drives the existing demo banner.

### Real implementation (stubbed)

`apps/web/src/lib/feed-queries.ts` holds the production queries as real
exported functions, unused until result-saving exists:

```ts
export async function loadFeedResults(
  viewerId: string,
  since: DateString,
): Promise<FeedItem[]> {
  const following = await prisma.follow.findMany({
    where: { followerId: viewerId },
    select: { followingId: true },
  });
  const ids = following.map((f) => f.followingId);
  if (ids.length === 0) return [];

  const rows = await prisma.gameResult.findMany({
    where: { userId: { in: ids }, playedDate: { gte: new Date(since) } },
    orderBy: [{ playedDate: "desc" }, { createdAt: "desc" }],
    include: { game: true, user: { select: { id: true, name: true, image: true } } },
    take: 200,
  });
  return rows.map(toFeedItem);
}
```

Plus `loadUserResults(userId, range)` for the profile page.

Switching over means changing `getFeedView` to call these instead of
`makeFixture`. The return type is identical, so no caller changes.

Notes carried in the file:

- `take: 200` stands in for pagination, which is out of scope.
- `playedDate` is `@db.Date`; the comparison must use a date-only value or
  results shift by a timezone.
- The `{ in: ids }` lookup is what makes the follow-graph index earn its place.

## Components

**New:** `FeedList` (day headers, rows of "name · game · 3/6 ✓"),
`ShareFollowLink` (your link plus a copy button).

**Reused unmodified:** `CalendarHeatmap`, `StatsSummary` on the profile page.

**Modified:** `AuthStatus` / layout gain a "Feed" link.

**Empty state:** following nobody shows your own share link and a line
explaining it, rather than a blank page.

## Error handling

| Case | Behaviour |
|---|---|
| Unknown/malformed code | "This follow link isn't valid" |
| Already following | Friendly note, not an error |
| Self-follow | Rejected in the action; `CHECK` constraint as backstop |
| Signed out | Redirect to sign-in, return to the same URL |
| Profile you don't follow | 404 |

## Testing

Pure logic moves into `packages/stats` so the existing `tsx --test` runner
covers it:

- `seedFrom(userId)` — determinism and distribution
- `mergeFeed(...)` — ordering across users, same-day ties, the 30-day cap
- `canViewProfile(viewerId, targetId, follows)` — pure predicate for the
  gating rule

`packages/stats/package.json` lists test files explicitly rather than globbing,
so its `test` script must be updated when files are added.

The thin remainder — the server action wrapping `prisma.follow.create` — has no
integration harness available and is verified by driving the running app in the
browser.

Tests are written before the implementation they cover.

## Open items

- Result persistence remains the blocker for real data; it is tracked
  separately and is not part of this work.
- Pagination, blocking, and code regeneration are deferred by choice.
